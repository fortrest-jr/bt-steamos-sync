# bt-steamos-sync

[English](README.md) | **Русский**

Утилита `bt-sync` копирует сопряжения Bluetooth из SteamOS во вторую систему Linux на том же Steam Deck (dual-boot). Устройства, сопряжённые в SteamOS, после этого работают и во второй системе без повторного сопряжения.

## Зачем

У обеих систем один адаптер Bluetooth с одним адресом. Но при сопряжении каждая система создаёт свой ключ, а устройство (наушники, клавиатура, мышь) помнит только последний ключ для этого адреса. В итоге:

- сопрягли наушники в SteamOS — в Mint они больше не подключаются;
- сопрягли заново в Mint — перестают подключаться в SteamOS.

Решение — сопрягать устройства только в SteamOS, а во вторую систему переносить те же ключи. Тогда обе системы для устройства выглядят одинаково, и переключаться между системами можно без перепривязки.

`bt-sync` делает этот перенос: читает записи BlueZ из SteamOS (`/var/lib/bluetooth/<адаптер>/<устройство>/info`) и записывает их в локальный `/var/lib/bluetooth`.

Готовых решений для пары SteamOS → Linux нет: существующие инструменты переносят ключи только между Windows и Linux.

## Установка

Нужны [uv](https://docs.astral.sh/uv/) и `sudo`; Python 3.12+ uv скачает сам, если его нет.

```bash
uv tool install git+https://github.com/fortrest-jr/bt-steamos-sync
```

Команда `bt-sync` появится в `~/.local/bin`. Обновить — `uv tool upgrade bt-steamos-sync`, удалить — `uv tool uninstall bt-steamos-sync`.

## Использование

```bash
bt-sync            # выбрать устройства в списке и скопировать
bt-sync --dry-run  # только показать, что изменится
bt-sync restore    # откатить одну из прошлых синхронизаций
```

Запускать от обычного пользователя: утилита спрашивает пароль sudo в начале (чтение требует root) и ещё раз проверяет sudo прямо перед записью, поэтому долгая пауза в списке запись не ломает. `restore` спрашивает пароль только перед записью. Под root работать отказывается.

Флаги:

| Флаг | Что делает |
|---|---|
| `--dry-run` | читает разделы и печатает план, ничего не меняет |
| `--keys-only` | заменяет только секции ключей, локальные имя и настройки устройства остаются |
| `--slot A\|B` | читать `var-A` или `var-B` вместо автоматического выбора |
| `--no-blueman` | не останавливать `blueman-applet`, пока bluetooth остановлен |

## Как работает

### 1. Чтение

- Локальное хранилище читается через `sudo tar` из `/var/lib/bluetooth`.
- SteamOS хранит Bluetooth на разделах `var-A` и `var-B` (A/B-обновления), путь внутри — `lib/bluetooth`. Разделы ищутся по `/dev/disk/by-partlabel/`.
- Раздел монтируется только для чтения с `ro,noload` (без воспроизведения журнала ext4) во временную папку и сразу размонтируется. Если раздел уже смонтирован — читается на месте.
- **На разделы SteamOS утилита никогда ничего не пишет.**
- Слот без `lib/bluetooth` считается пустым и запуск не прерывает.
- Каталог `cache` не читается и не копируется.

### 2. Выбор слота SteamOS

Нужно понять, какой из слотов A/B SteamOS загружала последним. Два маркера:

1. **Last mount time** из суперблока ext4 (`dumpe2fs -h`) — основной;
2. **время самой свежей записи** устройства для нашего адаптера.

Правила:

- слот, в котором нет локального адаптера, отбрасывается;
- остался один слот — берётся он;
- оба маркера указывают на один слот — берётся он без вопроса;
- маркер отсутствует или маркеры расходятся — утилита спрашивает и предлагает слот по времени монтирования;
- маркеров нет совсем — утилита тоже спрашивает.

### 3. План

Каждое устройство из SteamOS сравнивается с локальным по паре (адаптер, адрес устройства):

| Метка | Значение | Отмечено по умолчанию |
|---|---|---|
| `NEW` | в этой системе устройства нет | да |
| `REPLACE` | устройство есть, ключи отличаются | да |
| `SAME` | ключи совпадают | нет |

Сравниваются только секции ключей (`LinkKey`, `LongTermKey`, `PeripheralLongTermKey`, `SlaveLongTermKey`, `IdentityResolvingKey`, `LocalSignatureKey`, `RemoteSignatureKey`), отличие в имени или настройках не делает запись `REPLACE`.

Устройства, которые есть только в этой системе, в список не попадают и не трогаются: синхронизация идёт в одну сторону.

Список интерактивный (чекбоксы `questionary`), после выбора — отдельное подтверждение.

### 4. Запись

1. Останавливается `bluetooth.service`, чтобы работающий демон не перезаписал новые записи. Если запущен `blueman-applet`, он останавливается первым и запускается снова в конце: остановка службы при работающем апплете может зациклить включение и выключение адаптера (rfkill).
2. Заменяемые записи сохраняются в `~/.local/state/bt-sync/<ГГГГММДД-ЧЧММСС>/` вместе с `manifest.json` (что заменено, что добавлено).
3. Файл `info` записывается через `sudo install` с правами `600 root:root`. По умолчанию копируется целиком, с `--keys-only` в локальный файл подставляются только ключи.
4. `bluetooth.service` запускается снова, даже если запись не удалась.
5. Через `bluetoothctl devices` проверяется, что bluez загрузил все скопированные устройства. Незагруженные выводятся в отчёте.

### Откат

`bt-sync restore` показывает список бэкапов (новые сверху). Для выбранного бэкапа заменённые записи возвращаются, добавленные каталоги устройств удаляются; bluetooth на это время останавливается так же, как при синхронизации.

## Ограничения

- Поддерживается только направление SteamOS → текущая система.
- Разрабатывается и используется на Linux Mint. Из апплетов Bluetooth приостанавливается только `blueman-applet`, остальные не трогаются.
- Отдельной логики для контроллеров нет: они идут в общем списке, снимите отметку вручную, если не нужны.
- Проверено вживую: чтение обоих слотов, выбор слота и план (`--dry-run`). Пока не проверено: запись и `restore`.

## Разработка

Требования: [uv](https://docs.astral.sh/uv/), Python 3.12+.

```bash
uv sync                          # окружение и зависимости
uv run pytest                    # тесты
uvx ruff check .                 # линтер
uv tool install --editable .     # команда bt-sync в ~/.local/bin, правки подхватываются сразу
```

### Структура

```
src/bt_steamos_sync/
  cli.py              аргументы, сценарии sync и restore, проверка на root
  bluez_info.py       DeviceRecord, разбор и сборка info, сравнение и замена ключей
  bluetooth_store.py  чтение хранилища через sudo tar, StoreSnapshot
  steamos.py          разделы var-A/var-B, dumpe2fs, монтирование ro,noload
  slots.py            SlotState и выбор слота по маркерам
  plan.py             классификация NEW / REPLACE / SAME, построение плана
  apply.py            бэкап, запись через sudo install, manifest, restore
  services.py         остановка bluetooth на время записи, пауза blueman-applet, bluetoothctl
  privileged.py       обёртка над sudo (sudo -v для входа, sudo -n для команд)
  errors.py           BtSyncError, основа всех ошибок, которые выводятся без traceback
  ui.py               интерактивный список и подтверждения (questionary)
tests/
  conftest.py              адреса, генераторы info (classic_info, le_info), make_store_tar, FakeSudo
  test_bluez_info.py       разбор и замена ключей
  test_plan.py             классификация
  test_slots.py            разбор dumpe2fs и выбор слота
  test_store_and_apply.py  снимок из tar, apply/restore через FakeSudo, битые бэкапы
  test_cli.py              отказ под root, пустой план, порядок: проверка sudo, остановка, запись, запуск
```

### Как устроены тесты

- Системные вызовы идут только через объект `Sudo` (`privileged.py`). В тестах его заменяет `FakeSudo`: записывает вызовы и запоминает установленные файлы, ничего не выполняя.
- Хранилища BlueZ собираются в памяти как tar-архивы через `make_store_tar`, так же, как их отдаёт `sudo tar`.
- Каталог бэкапов уводится во временную папку фикстурой `state_home` (через `XDG_STATE_HOME`).
- Не покрыто тестами: реальное монтирование (`steamos.py`), работа с `blueman-applet` (`services.py`) и интерактивный UI (`ui.py`).
